## 一、30 秒项目定位话术

NightWatch 是我主导完成的生产级 AIOps 控制平面。它不是简单告警平台，而是把“告警接入 -> 语义诊断 -> 风险护栏 -> 自动修复 -> 恢复验证 -> 责任路由”做成可治理闭环。核心创新是：

- 用 LangGraph 管理状态机，让多分支流程可解释、可追踪；
- 用 FastMCP 把决策层和执行层物理隔离，降低误操作风险；
- 对 Flink Schema Drift 做硬熔断策略，防止错误数据扩散；
- 用 BM25 + 向量混合检索增强 RCA 证据质量。

一句话：**把大模型能力工程化成“能在夜里放心跑”的基础设施，而不是 Demo。**

## 三、架构抉择拷问（指定问题满分回答）

## Q1：为什么要用 LangGraph，而不是直接写 Python 脚本调 API？

### 短答版
因为我解决的是“状态驱动、可分支、可恢复、可审计”的故障处理问题，不是一次性函数调用问题。

### 深答版
如果只写脚本，通常会遇到四个结构性问题：
1. 分支复杂度爆炸：高风险审批、熔断、验证失败回退会让 if-else 迅速失控。
2. 状态不可恢复：进程重启后很难无损恢复上下文。
3. 可观测性差：难以知道流程卡在哪个节点、为何决策。
4. 演进成本高：每加一个节点都可能改动全链路。

LangGraph 的价值在于：
- 显式状态模型（AgentState）+
- 显式节点职责 +
- 显式条件路由 +
- checkpointer 持久化

这让系统具备 workflow 级工程属性，符合生产 AIOps 的治理要求。

---

## Q2：MCP 协议层是不是过度设计？实际价值是什么？

### 短答版
不是过度设计，它是“安全执行边界”。没有 MCP，LLM 编排层会直接拿到执行权限。

### 深答版
MCP 在这个项目里解决的是权限与可审计问题，不是语法糖问题：

- 决策层与执行层隔离：LangGraph 节点只能发工具调用，不直接触达外部系统。
- 角色权限控制：不同角色暴露不同工具，减少越权面。
- 统一审计：所有动作都经过工具网关，日志结构一致。
- 可替换性：mock connector -> 真实系统迁移时，流程逻辑稳定。

从架构角度看，MCP 是控制平面的“系统调用接口”。

## Q3：如果大模型夜间幻觉，乱改 Spark 参数导致集群瘫痪怎么办？

### 短答版
NightWatch 设计上不信任模型，模型建议必须经过多层护栏才可执行。

### 深答版
我用了四层防护：

1) 结构化输出约束
- LLM 通过 Instructor 输出 Pydantic 模型，避免任意文本解析。

2) 参数硬上限
- guardrail 对 executor memory、shuffle partitions 设定上界，超限直接 block。

3) 风险分级与审批门
- 风险高/关键场景进入 require_approval，未批准不执行。

4) 恢复验证与熔断
- 执行后必须 verify_recovery，不恢复则升级处理或熔断，不继续盲目重试。

本质策略：**默认不信任模型，执行以规则为准，规则优先级高于模型建议。**

## 四、深水区追问与高分回答

## 1) Flink Schema Drift 的底层识别原理是什么？

### 面试官追问点
- 如何降低误判漏判？
- 为什么要物理熔断而不是重试？

### 满分回答
我的 Drift 识别不是单点关键词，而是“信号融合 + 结构化提取”：

- 信号层：unsupported cdc data type / column type mismatch / ddl changed 等 marker。
- 结构层：提取 table、column、old_type、new_type。
- 语义层：结合 incident_type 与日志证据构造诊断对象（risk=critical, requires_circuit_break=true）。

为什么要熔断：
- 这类故障不是资源瞬时抖动，而是数据契约破坏。
- 盲目重试只会反复失败，甚至将异常数据写入下游。
- 所以必须 pause + suspend downstream，先止血再修 schema。

---

## 2) 混合检索（BM25 + 向量）的融合策略与工程权衡？

### 面试官追问点
- 为什么不用纯向量？
- 融合权重如何定？

### 满分回答
我采用 lexical + semantic 双路召回：

- BM25 对错误签名、异常码、关键短语命中很强（精确词匹配）。
- 向量检索对同义描述和上下文鲁棒（语义泛化）。

融合方式：
- 对两路分数先归一化，再做线性融合：score = 0.6 * bm25 + 0.4 * vector。
- 0.6/0.4 的原因：在运维故障文本中，关键字精确命中通常更稳定，向量用于补召回。

降级策略：
- Qdrant 不可用时自动回退 lexical-only，不阻塞主流程。

---

## 3) 告警风暴下（Correlator）如何控并发与去噪？

### 面试官追问点
- 同一事故多次告警如何处理？
- 如何避免重复动作执行？

### 满分回答
我的策略是“时间窗口聚合 + 主事件选举 + 证据合并”：

- correlation key 优先用 application_id，其次 job_name。
- 在窗口内（默认 120s）把同 key 事件聚成一组。
- 组内按严重等级 + 时间选择 primary incident。
- 合并日志片段和指标并去重，写入 correlated_event_count。

收益：
- 把 N 条噪声告警收敛成 1 条可执行事件。
- 避免重复触发自愈动作，降低执行风暴风险。
