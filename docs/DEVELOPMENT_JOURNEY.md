# NightWatch 架构演进与开发纪实

## 前言

NightWatch 的目标从一开始就不是“做一个会回复的 AI Demo”，而是做一个在夜间无人值守窗口也敢执行自动动作的生产级 AIOps 控制平面。

这条路线的核心矛盾非常明确：

- 一方面，我们需要 LLM 的推理能力去做跨系统语义诊断。
- 另一方面，我们不能把生产执行权限直接暴露给一个不可完全预测的大模型。

因此，NightWatch 的演进主线不是“加功能”，而是“加约束”：
从感知，到诊断，到自愈，再到审计、护栏、执行边界和可观测体系，逐层收敛到可上线形态。

---

## M1 -> M5：从 0 到 1 的里程碑

## M1 感知骨架（Perception Skeleton）

### 目标
把多源告警先接住、先归一，不丢事件、不乱格式。

### 关键产物
- 统一事件模型（IncidentEvent / AgentState）。
- Ingest API 入口与标准化字段（cluster、job_name、error_signature、labels、metrics）。
- 最小可运行状态机骨架（ingest -> diagnose 占位）。

### 架构收益
- 消除了各引擎日志风格差异带来的数据入模成本。
- 为后续关联聚合和诊断推理打下统一语义底座。

---

## M2 诊断闭环（Diagnosis Loop）

### 目标
让系统不只“知道坏了”，还要“知道为什么坏”。

### 关键产物
- Spark RCA 诊断器。
- Flink Schema Drift 识别器（关键 marker + 表字段与类型变化提取）。
- 检索增强：BM25 + 向量检索混合召回历史 case。

### 架构收益
- 诊断从静态规则升级为“规则 + 检索证据”的可解释组合。
- 为修复规划提供结构化根因输入（incident_type、risk_level、recoverable）。

---

## M3 自愈执行链（Try-Heal-Retry）

### 目标
从“建议动作”升级到“可控执行”。

### 关键产物
- heal planner（可规则、可 LLM 结构化生成）。
- 执行器与恢复验证器。
- execution_records 审计轨迹。

### 架构收益
- 打通 diagnose -> plan -> execute -> verify 的闭环。
- 支持“受控重试”而不是盲目重跑，降低二次事故概率。

---

## M4 风险门禁与责任路由（Safety & Accountability）

### 目标
给自动化动作加“刹车系统”，把误伤概率压到可接受区间。

### 关键产物
- Guardrails：
  - 参数上界（executor memory / shuffle partitions）。
  - 高风险强制审批。
  - circuit break 场景禁止自动重试。
  - Schema Drift 禁止 tune_and_retry。
- 通知与责任路由（GitHub/Jira）。

### 架构收益
- 自动化从“能执行”升级为“可治理执行”。
- 每个动作有证据、有边界、有责任主体。

---

## M5 生产增强（Production Hardening）

### 目标
补齐企业化落地最后一公里：部署、观测、前端可用性、协议解耦。

### 关键产物
- Docker Compose 生产编排（API + Worker + MCP + Qdrant + Prometheus + Grafana）。
- Next.js 企业级控制台（总览、演练、配置分区）。
- 运行时配置中心（GET/PUT runtime-config，敏感字段掩码更新）。
- 核心测试全绿（22 项关键场景）。

### 架构收益
- 进入可开箱部署、可观测、可演示、可扩展的工程状态。

---

## 架构升维 1：前端重构，不再“AI Demo 味”

## 旧问题
早期前端存在两个典型问题：
- 视觉与交互偏“实验性质”，缺少生产控制台的层级感。
- 功能堆叠在单页，信息密度过高，操作路径混乱。

## 重构策略
- 设计语言从“赛博炫酷”切换到“企业 SaaS 运营台”。
- 页面按任务分区：运行总览 / 事件演练 / 集群配置。
- 将连接信息、风险状态、日志流、快照、配置操作进行职责拆分。

## 结果
- 降低首次理解成本，提升现场演示与面试讲解效率。
- 运维操作链路更清晰，减少误触与配置混乱。

---

## 架构升维 2：引入 FastMCP，彻底解耦“大脑”和“触手”

## 为什么不是让 LangGraph 节点直接调连接器
如果节点直接访问外部系统，会出现三类工程问题：
- 权限边界不清：编排逻辑天然拥有执行权限。
- 审计面分裂：难以统一记录工具级动作。
- 运行形态僵化：后续接入远端工具网关会牵一发动全身。

## FastMCP 的价值
- 协议层解耦：决策层仅做工具调用，不关心底层执行实现。
- 权限控制：按角色注册工具（agent/oncall/admin）。
- 审计一致性：所有动作收敛到工具调用事件。
- 可替换性：未来从 mock connector 平滑迁移到真实引擎。

## 一句话总结
LangGraph 决策“做什么”，MCP 决定“怎么安全地做”。

## 踩过的坑与关键重构

## 1) 恢复验证闭环不完整
### 问题
早期只记录“执行了 retry”，但没有严格判断“是否真正恢复”。

### 后果
可能产生“动作成功但业务仍失败”的假阳性。

### 解决
- 引入 verifier 节点，强制拉取调度任务状态。
- 只有 RUNNING / SUCCESS 才判定 recovered。
- 否则进入 degraded/escalation 分支并写审计。

---

## 2) Schema Drift 识别过于脆弱
### 问题
仅靠单关键词匹配，容易漏判或误判。

### 解决
- 增加 marker 组合信号。
- 增加 table/column/type change 结构化提取。
- 在 guardrail 侧增加硬约束：Schema Drift 禁止自动 tune_and_retry。

### 效果
高危场景路径稳定落到 circuit break 与责任通知。

---

## 3) Qdrant 兼容与依赖降级
### 问题
不同环境下 qdrant-client、collection/search 接口差异导致运行不稳定。

### 解决
- 检索模块实现 ImportError fallback。
- 向量查询 API 做兼容分支（search / query_points）。
- 向量路径不可用时退回 lexical-only，避免流程阻塞。

### 效果
检索链路“可增强但不强依赖”，在演示与生产场景都更稳。

---

## 4) 前后端联调中的开发体验问题
### 问题
- Next 开发态 origin 校验导致页面看似无响应。
- FastAPI 旧进程导致 CORS preflight 405。

### 解决
- 配置 allowedDevOrigins。
- 明确 CORS 来源并重启 API 进程使中间件生效。

### 收益
减少“看起来像业务 Bug，实际是开发态配置”的排障成本。

---

## 5) 运行时配置与持久化边界
### 问题
用户希望在前端统一配置所有连接器；但直接写死到代码或环境变量风险大。

### 解决
- 增加 runtime-config API，支持运行时更新并掩码敏感字段。
- 明确 persisted=false 语义：重启后回到环境配置。

### 下一步
接入持久化配置存储（例如 SQLite 配置表 + 版本审计 + 回滚）。

---

## 工程方法论沉淀

- **先建约束，再放能力**：护栏、审批、审计优先于“多动作自动化”。
- **先可观测，再可自治**：每一步必须可解释、可追踪、可回放。
- **分层解耦，反脆弱演进**：LangGraph 负责编排，MCP 负责执行边界，Connector 负责外部协议映射。

---

## 后续路线（Open Source 版本）

- MCP 工具从 mock 迁移到真实 Spark/Flink/Scheduler 驱动。
- 增加多租户与命名空间隔离。
- 引入策略引擎（如 OPA）进行可审计规则治理。
- 增加 chaos 场景回归集，验证告警风暴下的自愈稳定性。

---

## 结语

NightWatch 的真正价值不在于“能不能调用大模型”，而在于：
**在生产故障场景下，如何把大模型的推理能力约束进一条可治理、可审计、可回退、可验证的工程管道。**

这也是它作为基础架构与 AIOps 项目的核心竞争力。
